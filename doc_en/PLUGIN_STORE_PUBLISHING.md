# OpenSquad Plugin Development & Store Publishing Guide

This guide is for developers who want to publish their plugins to the OpenSquad Plugin Store. It covers the complete workflow: environment setup, implementation, local testing, submitting a registration Issue for review, publishing, and releasing updates.

---

## End-to-End Overview

```
Set up development environment
    │
    ▼
Write plugin code (plugin.py + plugin.json + README.md)
    │
    ▼
Local testing (syntax → load → functional)
    │
    ▼
Push plugin code to your own GitHub repository
    │
    ▼
Submit an Issue to the plugin registry repository
  (include: plugin_id, git_url, version, description, etc.)
    │
    ▼ Automated code review bot (static checks + AI code review)
    │
    ▼ Maintainer approves → writes plugin metadata to registry index
    │
    ▼
Plugin appears in the OpenSquad Plugin Market
  (users install with one click; downloaded from your repository)
```

## II. Plugin Implementation Specification

### 2.1 Naming Rules (Enforced)

The plugin ID is derived automatically from the plugin name using this algorithm:

```
Original name → lowercase → spaces and hyphens replaced with underscores
             → remove non-alphanumeric/underscore characters
             → collapse consecutive underscores → strip leading/trailing underscores
```

Examples:

| `name` you provide | Generated `plugin_id` | Note |
|---|---|---|
| `Web Search` | `web_search` | Space → underscore |
| `Rate-Limiter` | `rate_limiter` | Hyphen → underscore |
| `My Awesome Plugin v2` | `my_awesome_plugin_v2` | Mixed case |
| `HTTP/2 Proxy` | `http2_proxy` | `/` removed |

**Key constraints (must be followed):**

1. The `name` in `@register(name=...)` **must** equal the generated plugin_id
2. The plugin directory name **must** equal the plugin_id
3. The plugin_id is **globally unique** in the store, case-insensitive, first-come-first-served
4. The name cannot be changed after publishing (changes will be rejected by the server)

> **Verify uniqueness before naming:** Open the Plugin Market and search for your intended name to confirm no plugin with the same name exists.

### 2.2 Directory Structure (Required)

```
plugins/
└── {plugin_id}/
    ├── __init__.py          # Empty file, Python package marker — required
    ├── plugin.py            # Required; must contain exactly one @register-decorated class
    ├── plugin.json          # Auto-generated by the framework; do not create or edit manually
    ├── README.md            # Recommended: installation instructions, config field descriptions
    └── (other modules)      # Optional helpers: storage.py, utils.py, etc.
```

`plugin.json` is **overwritten automatically every time the framework loads**; manual edits have no effect. Version, description, and all other metadata are taken from the `@register` declaration.

### 2.3 plugin.py Specification

#### Minimal Valid Structure

```python
# plugins/my_plugin/plugin.py
from opensquad.plugin_api import register, Plugin, Context

@register(
    name="my_plugin",           # Must equal plugin_id (directory name)
    author="Your Name",
    description="One-sentence description of what this plugin does",
    version="1.0.0",
    plugin_type="tool",         # "tool" | "hook" | "platform"
    display_name="My Plugin",
)
class MyPlugin(Plugin):
    def __init__(self, context: Context):
        super().__init__(context)

    def on_load(self) -> None:
        """Called when the plugin loads. Initialize resources, DB connections, etc."""
        pass

    def on_unload(self) -> None:
        """Called when the plugin unloads/is disabled. Release resources, close connections, etc."""
        pass
```

#### @register Full Parameter Reference

| Parameter | Type | Required | Description |
|---|---|---|---|
| `name` | str | Yes | plugin_id; must match the directory name exactly |
| `author` | str | Yes | Author name; must match the store record for version updates (used for ownership verification) |
| `description` | str | Yes | Functional description; shown on the store card |
| `version` | str | Yes | Semantic version, e.g. `"1.0.0"` |
| `plugin_type` | str | Yes | `"tool"` / `"hook"` / `"platform"` |
| `display_name` | str | No | Display name; auto-generated if omitted |
| `config_schema` | dict | No | User-configurable fields; see Section 2.5 |
| `dependencies` | dict | No | `{"pip": ["requests", "httpx"]}` |
| `contributes` | dict | No | Frontend view contributions; see Section 2.6 |
| `tags` | list | No | Search tags, e.g. `["search", "web"]` |

### 2.4 Complete Templates for All Three Plugin Types

#### Type 1: Tool Plugin (tool)

Tool plugins provide callable tool functions to Agents.

```python
# plugins/my_search/plugin.py
import logging
from opensquad.plugin_api import register, tool, Plugin, Context

logger = logging.getLogger("plugins.my_search")


@register(
    name="my_search",
    author="Your Name",
    description="Custom search tool: retrieves information from a specified data source",
    version="1.0.0",
    plugin_type="tool",
    display_name="My Search",
    dependencies={"pip": ["requests"]},
    tags=["search", "api"],
)
class MySearchPlugin(Plugin):
    def __init__(self, context: Context):
        super().__init__(context)
        self._api_key: str = ""

    def on_load(self) -> None:
        self._api_key = self.context.config.get("api_key", "")
        logger.info(f"[MySearch] loaded (agent={self.context.agent_id})")

    def on_unload(self) -> None:
        logger.info("[MySearch] unloaded")

    @tool(
        name="my_search",           # Tool namespace; used by the Agent when calling this tool
        description="Search a custom data source",
        level="core",               # "core"=full docs  "extended"=summary docs
        auto_register=False,        # True=auto-register to all Agents
    )
    def search(self, query: str, max_results: int = 10):
        """
        Search a custom data source.

        Args:
            query:       Search keywords
            max_results: Maximum number of results to return (default 10)

        Returns:
            list[dict]: List of results with title, url, snippet fields
        """
        import requests
        results = []
        try:
            resp = requests.get(
                "https://your-api.example.com/search",
                params={"q": query, "n": max_results, "key": self._api_key},
                timeout=10,
            )
            resp.raise_for_status()
            for item in resp.json().get("items", []):
                results.append({
                    "title": item["title"],
                    "url": item["url"],
                    "snippet": item.get("snippet", ""),
                })
        except Exception as e:
            return f"Error: {e}"
        return results
```

> A single class can have **multiple** `@tool` methods sharing the same `name` (tool namespace). These methods are combined into a single tool module available to Agents.

#### Type 2: Hook Plugin (hook)

Hook plugins intercept Agent lifecycle events and can modify inputs/outputs or collect data.

```python
# plugins/my_filter/plugin.py
import logging
from opensquad.plugin_api import register, hook, on_event, Plugin, Context

logger = logging.getLogger("plugins.my_filter")


@register(
    name="my_filter",
    author="Your Name",
    description="Message filter and audit plugin: blocks sensitive words and logs all conversations",
    version="1.0.0",
    plugin_type="hook",
    display_name="My Filter",
    config_schema={
        "blocked_words": {
            "type": "string",
            "default": "",
            "description": "Comma-separated list of blocked words, e.g.: spam,ads,scam",
        },
    },
    tags=["security", "filter"],
)
class MyFilterPlugin(Plugin):
    def __init__(self, context: Context):
        super().__init__(context)
        self._blocked: list = []

    def on_load(self) -> None:
        raw = self.context.config.get("blocked_words", "")
        self._blocked = [w.strip().lower() for w in raw.split(",") if w.strip()]
        logger.info(f"[MyFilter] loaded, {len(self._blocked)} blocked words")

    def on_unload(self) -> None:
        logger.info("[MyFilter] unloaded")

    @hook.on_message_received
    async def filter_message(self, context: dict) -> dict:
        """
        Intercept messages containing blocked words.

        context fields: message, channel, sender_name, chat_name,
                        source_chat_id, input_source
        Special control: set context['__stop__'] = True to discard the message
        """
        message = context.get("message", "").lower()
        for word in self._blocked:
            if word in message:
                logger.warning(f"[MyFilter] Blocked message from {context.get('sender_name')}")
                context["__stop__"] = True
                return context
        return context

    @hook.on_after_tool
    async def log_tool(self, context: dict) -> dict:
        """
        Log every tool call (without modifying the result).

        context fields: tool_name, arguments, result, agent_id, model
        Modify context['result'] to override the tool return value.
        """
        logger.info(
            f"[MyFilter] tool={context.get('tool_name')} "
            f"result_len={len(str(context.get('result', '')))}"
        )
        return context  # Hook methods must return context
```

**All available hooks (13 total):**

| Hook name | Triggered when | Modifiable fields | Special control |
|---|---|---|---|
| `on_message_received` | User message arrives | — | `__stop__=True` discards message |
| `on_before_llm` | Before LLM call | `messages` (list) | `__stop__=True` skips LLM |
| `on_after_llm` | After LLM response | `response` (str) | — |
| `on_before_tool` | Before tool call | `arguments` | `skip=True` + provide `result` to skip execution |
| `on_after_tool` | After tool call | `result` (str) | — |
| `on_tool_error` | After tool error | `error` (str) | — |
| `on_before_send` | Before reply is sent | `message` (str) | `__stop__=True` cancels sending |
| `on_after_send` | After reply is sent | — | — |
| `on_before_prompt` | Before system prompt is finalized | `prompt` (str) | — |
| `on_task_start` | Task begins | — | — |
| `on_task_complete` | Task ends | — | — |
| `on_state_change` | Agent state transitions | — | — |

All hooks support a priority parameter (higher number executes first):

```python
@hook.on_after_tool(priority=100)   # Executes before other hooks
async def high_priority_hook(self, context: dict) -> dict:
    ...
```

#### Type 3: Platform Plugin (platform)

Platform plugins integrate external IM platforms, providing an inbound message adapter and outbound sending tools.

```python
# plugins/my_platform/plugin.py
import importlib
import logging
from typing import Any, Dict, List

from opensquad.plugin_api import register, Plugin, Context

logger = logging.getLogger("plugins.my_platform")


@register(
    name="my_platform",
    author="Your Name",
    description="MyPlatform adapter: receives messages and provides sending tools",
    version="1.0.0",
    plugin_type="platform",
    display_name="My Platform",
    dependencies={"pip": ["requests"]},
    tags=["im", "platform"],
)
class MyPlatformPlugin(Plugin):
    def __init__(self, context: Context):
        super().__init__(context)

    def on_load(self) -> None:
        logger.info("[MyPlatform] loaded")

    def on_unload(self) -> None:
        logger.info("[MyPlatform] unloaded")

    def get_tool_modules(self) -> List[Dict[str, Any]]:
        """
        Proxy mode: registers a standalone tool module file as tools.
        Suitable when tool logic is complex or a legacy implementation already exists.
        """
        tools = []
        try:
            module = importlib.import_module("plugins.my_platform.send_tools")
            tools.append({
                "name": "my_platform_send",
                "module": module,
                "level": "extended",
                "auto_register": True,
                "requires_agent_id": True,
            })
        except ImportError as e:
            logger.error(f"[MyPlatform] Cannot import send_tools: {e}")
        return tools
```

### 2.5 User-Configurable Fields (config_schema)

Declaring `config_schema` in `@register` causes the admin UI to automatically generate a settings panel.

```python
config_schema={
    "api_key": {
        "type": "string",
        "default": "",
        "description": "API key (obtain from your provider's console)",
    },
    "timeout_sec": {
        "type": "integer",
        "default": 10,
        "description": "Request timeout in seconds",
    },
    "enable_cache": {
        "type": "boolean",
        "default": True,
        "description": "Whether to cache search results",
    },
    "base_url": {
        "type": "string",
        "default": "https://api.example.com",
        "description": "API service URL; change this for self-hosted deployments",
    },
},
```

Supported types: `string`, `integer`, `number`, `boolean`

Reading config in `on_load()`:

```python
def on_load(self) -> None:
    api_key   = self.context.config.get("api_key", "")
    timeout   = self.context.config.get("timeout_sec", 10)
    use_cache = self.context.config.get("enable_cache", True)
    base_url  = self.context.config.get("base_url", "https://api.example.com")
```

Config merge order: `config_schema defaults` → `values saved by the user in the UI` (stored in `data/plugins/{name}/config.json`)

### 2.6 Data Persistence

Use `self.context.data_dir` to get the plugin's dedicated data directory (the framework guarantees the directory exists):

```python
import json, os

def on_load(self) -> None:
    self._data_file = os.path.join(self.context.data_dir, "records.json")
    # data_dir = data/plugins/{plugin_name}/
```

**JSON file persistence (small data):**

```python
def _load(self) -> list:
    if not os.path.exists(self._data_file):
        return []
    with open(self._data_file, "r", encoding="utf-8") as f:
        return json.load(f)

def _save(self, data: list) -> None:
    with open(self._data_file, "w", encoding="utf-8") as f:
        json.dump(data, f, ensure_ascii=False, indent=2)
```

**SQLite persistence (large data / needs querying):**

```python
import sqlite3

def on_load(self) -> None:
    db_path = os.path.join(self.context.data_dir, "data.db")
    self._conn = sqlite3.connect(db_path, check_same_thread=False)
    self._conn.execute("""
        CREATE TABLE IF NOT EXISTS records (
            id INTEGER PRIMARY KEY AUTOINCREMENT,
            content TEXT,
            created_at TEXT
        )
    """)
    self._conn.commit()

def on_unload(self) -> None:
    if self._conn:
        self._conn.close()
        self._conn = None
```

## III. Local Testing Specification

Before submitting for review, complete the following three testing steps.

### 3.1 Syntax Check

```bash
python -m py_compile plugins/{plugin_id}/plugin.py
```

**No output = syntax is correct.** Syntax errors cause silent load failures with no obvious indication in the logs.

### 3.2 Load Verification

Add the plugin name to the target Agent's `config.json` (in the `tools` list), then restart the Agent process:

```bash
# Restart via Launcher HTTP API (port 9600)
POST http://127.0.0.1:9600/api/agents/{agent_dir_name}/restart
```

After restarting, verify both of the following:

1. The Agent log contains `[PluginManager] Loaded plugin: {plugin_id}` with no ERROR
2. In the admin "Plugin Manager" page, the plugin status is **Enabled**

> For **new plugins** (first load), one restart is sufficient. For **subsequent code changes**, each modification to a `.py` file requires a restart — hot-reload only applies to configuration changes and enable/disable toggles; it cannot re-import modified modules.

### 3.3 Functional Testing

Call the tool in an Agent conversation to verify end-to-end functionality:

```
# Tool plugin test
my_search.search(query="test query", max_results=5)

# Hook plugin test (send a message containing a blocked word and verify it is filtered)
```

Verify:

- [ ] Tool call succeeds and returns the expected format
- [ ] Invalid input produces a reasonable error message (returns `"Error: ..."` string rather than raising an exception)
- [ ] `on_unload()` shuts down cleanly (no exceptions in the log on restart)
- [ ] Data files are located under `data/plugins/{plugin_id}/`, not in the code directory

### 3.4 Common Load Errors

| Symptom | Cause | Fix |
|---|---|---|
| Plugin not shown in Plugin Manager | `plugin.py` missing or has syntax error | Check with `python -m py_compile` |
| Loaded successfully but tool unavailable | `@register(name=...)` does not match directory name | Keep both identical |
| `ModuleNotFoundError` | Dependency not installed | `pip install -r requirements.txt` |
| `on_load` throws error | Initialization logic exception | Add `try/except` to prevent blocking the load |
| Still running old code after hot-reload | Modified a `.py` file, only triggered hot-reload | Must restart the Agent process |

## IV. Publishing Plugins to the Registry

### 4.1 Prerequisites

- A GitHub account
- Basic Git operations (clone, push)
- Completed local testing from Chapter III

### 4.2 Push Your Plugin to Your Own GitHub Repository

```bash
# 1. Create a new repository on GitHub, e.g. https://github.com/{your_github_username}/{plugin_id}

# 2. Initialize and push from your local plugin directory
cd plugins/{plugin_id}
git init
git add .
git commit -m "feat: initial release v1.0.0"
git remote add origin https://github.com/{your_github_username}/{plugin_id}.git
git push -u origin main
```

The repository root should have this structure:

```
{plugin_id}/          ← repository root (= plugin directory)
├── __init__.py
├── plugin.py
├── plugin.json       ← store format; see Section 4.3
├── requirements.txt  ← optional but strongly recommended
└── README.md         ← optional but recommended
```

### 4.3 plugin.json Format

The plugin directory must contain a `plugin.json` in the following format:

```json
{
  "id": "my_plugin",
  "name": "My Plugin",
  "version": "1.0.0",
  "description": "Brief description of what the plugin does",
  "author": "YourGitHubUsername",
  "type": "tool",
  "tags": ["example"],
  "homepage": "https://github.com/yourname/my_plugin",
  "git_url": "https://github.com/yourname/my_plugin"
}
```

**Required fields:** `id`, `name`, `version`, `description`, `author`, `type`

- `id` must match the directory name exactly (and must also match `@register(name=...)` in `plugin.py`).
- `git_url` is the true installation source — the system downloads plugin code from this URL when a user installs.
- `homepage` is usually the same as `git_url`, or can point to documentation/demo pages.

### 4.4 Submit a Registration Issue

Go to the plugin registry repository at [**github.com/opensquad-ai/opensquad-plugins**](https://github.com/opensquad-ai/opensquad-plugins), click **New Issue**, select the **"Submit a Plugin"** template, and fill in the following:

```
plugin_id:    my_plugin
Display name: My Plugin
Version:      1.0.0
Type:         tool
Description:  Brief description of what the plugin does
Author (GitHub username): YourGitHubUsername
git_url:      https://github.com/YourGitHubUsername/my_plugin
Tags (optional): example, api
```

Suggested Issue title format: `[Plugin] Plugin Display Name (plugin_id)`

### 4.5 Automated Code Review

After the Issue is submitted, a bot automatically pulls code from `git_url` and performs:

1. **Static checks**
   - `plugin.json` required field completeness
   - `plugin.py` syntax validity (`ast.parse`)
   - Presence of the `@register` decorator
   - Inheritance of the `Plugin` base class
   - Security scan (dangerous calls: `subprocess`, `eval`, `exec`, `os.system`, etc.)

2. **AI code review**
   - Code quality and readability
   - Consistency between description and implementation
   - In-depth security analysis

Review results are posted automatically as an Issue comment in the following format:

```
## OpenSquad Plugin Automated Review Report ✅

**Overall verdict**: PASS — Recommended for inclusion

### Static Checks
No static check issues

### AI Code Review
Code structure is clear, correctly inherits the Plugin class and uses the @register decorator...
```

Overall verdicts have three levels:
- **PASS** — Recommended for inclusion
- **WARN** — Recommended to revise before inclusion (specific feedback in the comment)
- **FAIL** — Recommended to reject (security issue or specification violation)

### 4.6 Human Review and Inclusion

Maintainers use the AI review results as a reference during manual review. Once approved, the maintainer writes the plugin metadata to the registry index file, making the plugin discoverable and installable.

### 4.7 Post-Inclusion Publishing Flow

```
Maintainer writes plugin metadata to registry index
    │
    ▼
Plugin Market reads index → displays plugin card (name, description, version, author)
    │
    ▼
User clicks "Install"
    │
    ├── System downloads code from git_url (your repository)
    │
    ├── If repository contains pre-built artifacts (e.g. ui/index.js) → install directly
    │
    └── If no pre-built artifacts → automatically trigger build (e.g. npm run build)
```

## V. Releasing Version Updates

### 5.1 Version Numbering

Follow Semantic Versioning (SemVer):

| Type | Version change | When to use |
|---|---|---|
| Patch | `1.0.0` → `1.0.1` | Bug fixes, documentation updates |
| Minor | `1.0.0` → `1.1.0` | New features, backwards compatible |
| Major | `1.0.0` → `2.0.0` | Breaking changes (tool name / parameter changes) |

**"Update available" badge logic:** When the registry version > the user's installed version, the plugin card shows an "Update vX.Y.Z" button (yellow).

### 5.2 Submitting a Version Update

The process is identical to the initial publish: modify code → update `version` in `plugin.json` → submit PR → merged and auto-published.

`publish.yml` detects the version number change and automatically creates a new Release and syncs the registry.

### 5.3 Ownership Protection

The registry records plugin ownership via the `github_user` field (taken from the PR author's GitHub username). Subsequent update PRs for the same plugin_id must come from the same GitHub user; otherwise the sync endpoint will reject the write.

## VI. Post-Install Usage Flow (For Reference)

Understanding the user-side flow helps you design a better plugin interaction experience:

```
User clicks "Install" in the store
    │
    ▼
Backend POST /api/ai-web/market/plugins/{id}/install
    │
    ├── 1. Fetch metadata from plugin registry (includes version, download_url)
    │
    ├── 2. Check locally installed version and enabled state
    │
    ├── 3. Download ZIP from GitHub Release
    │
    ├── 4. Extract to plugins/{plugin_id}/ (handles top-level wrapper directory automatically)
    │
    ├── 5. Restore enabled state to plugin.json
    │
    └── 6. Write to plugins/.reload_ts → triggers hot-reload (takes effect within 5 seconds)
```

**Activating tool-type plugins** (manual step required by user):

Edit `agents/{agent_dir}/config.json`, add the plugin ID to the `tools` list, then restart the Agent process.

## VII. User Activation Flow After Install (For Reference)

```
User clicks "Install" in the store
    │
    ▼
Plugin code downloaded from GitHub Release to plugins/{plugin_id}/
    │
    ▼
Framework hot-reload (no restart needed)
    │
    ▼
Plugin appears in admin "Plugin Manager" (enabled=true)
    │
    ├── Tool plugins:  Add plugin_id to the Agent config's tools list
    │                  Then restart the Agent process (tool registration requires restart)
    │
    └── Hook / Platform plugins: Take effect immediately after hot-reload, no restart needed
```

**Activating tool-type plugins** (manual step required by user):

Edit `agents/{agent_dir}/config.json` and add:

```json
{
  "tools": [
    "existing_tool_1",
    "web_search_pro"    ← new entry
  ]
}
```

Then restart the Agent process. The Agent can then call `web_search_pro.{function_name}(...)` tools.

## VIII. Complete Publishing Checklist

### Code Standards

- [ ] `plugin.py` contains exactly one `@register`-decorated class
- [ ] `@register(name=...)` matches the directory name exactly
- [ ] An empty `__init__.py` exists in the directory
- [ ] `on_load()` and `on_unload()` are implemented
- [ ] Tool methods have docstrings (including Args and Returns descriptions)
- [ ] All exceptions are caught; tools return `"Error: ..."` strings (not raised exceptions)
- [ ] All file paths are based on `context.data_dir` or `context.project_root`; no hardcoded absolute paths
- [ ] Sensitive data such as API keys is declared via `config_schema`, not hardcoded
- [ ] All third-party pip packages are declared in `dependencies`
- [ ] `on_unload()` closes all resources opened in `on_load()`
- [ ] **No dangerous calls** (`subprocess`, `eval`, `exec`, `os.system`, etc.) — the AI review bot detects these automatically

### plugin.json Standards

- [ ] `id` matches the directory name and `@register(name=...)`
- [ ] `name`, `version`, `description`, `author`, `type` are all filled in
- [ ] `type` is one of `"tool"`, `"hook"`, `"platform"`
- [ ] `version` follows semantic version format (e.g. `"1.0.0"`)

### Local Testing

- [ ] `python -m py_compile plugins/{plugin_id}/plugin.py` passes with no errors
- [ ] Agent log shows `Loaded plugin: {plugin_id}` with no ERROR
- [ ] Tool / hook functionality works correctly and results are in the expected format
- [ ] Invalid inputs (empty strings, None, oversized inputs) produce reasonable responses
- [ ] Plugin recovers correctly after Agent restart with no state leakage

### GitHub Issue Submission

- [ ] Created your own GitHub repository for the plugin
- [ ] Repository root directory named as plugin_id (no spaces; lowercase letters/digits/underscores only)

## IX. Common Errors Quick Reference

| Error | Cause | Fix |
|---|---|---|
| AI review: missing @register | `plugin.py` has no @register decorator | Add the decorator following the spec |
| AI review: security check failed | Uses subprocess/eval/exec etc. | Replace with safe alternatives |
| AI review: plugin.json parse failed | JSON format error | Validate with a JSON linter |
| AI review: id does not match directory name | `id` field in `plugin.json` is wrong | Keep id, directory name, and @register name identical |
| Plugin not in market after merge | `publish.yml` failed | Check GitHub Actions logs |
| Plugin installed but Agent cannot call tool | Tool-type plugin not added to tools list | Edit `config.json` → `tools`, restart Agent |
| Plugin appears but status is disabled | `plugin.json` enabled=false | Enable manually in the Plugin Manager page |
| Update button not shown after version update | New version ≤ installed version | Use a higher version number |
| Code not updated after hot-reload | Modified a `.py` file (requires restart) | `POST /api/agents/{dir}/restart` |

## Appendix: Plugin ID Validator

Run this script locally before publishing to verify your plugin_id:

```python
import re

def name_to_id(name: str) -> str:
    s = name.lower().strip()
    s = re.sub(r"[\s\-]+", "_", s)
    s = re.sub(r"[^a-z0-9_]", "", s)
    s = re.sub(r"_+", "_", s).strip("_")
    return s or "plugin"

# Validation examples
names = [
    "My Awesome Plugin",
    "Web Search Pro",
    "Rate-Limiter v2",
    "HTTP/2 Proxy Tool",
]
for name in names:
    plugin_id = name_to_id(name)
    print(f"{name!r:30s} -> {plugin_id!r}")
    print(f"  @register(name={plugin_id!r}, ...)")
    print(f"  Directory: plugins/{plugin_id}/")
```
